# Next Steps

## 1. Reduce false positives

- Change the review prompt to require high confidence before returning a comment.
- Tell Gemini to return no comment when project-wide intent cannot be established.
- Add an explicit distinction between a provable defect and an intentional logic mismatch.
- Include a confidence field in the response and discard comments below a configurable threshold.

Acceptance criteria:

- Suggestions identify a concrete, actionable defect.
- Uncertain behavior produces no comment instead of speculation.
- Existing line numbers and comment rendering remain unchanged.

## 2. Resolve related workspace symbols

- Use VS Code definitions and references APIs for symbols in the selected code.
- Include only directly referenced functions, methods, types, and constants from nearby workspace files.
- Include relevant tests or call sites when they are cheap to locate.
- Deduplicate context and preserve source file names and absolute line numbers.

Acceptance criteria:

- Cross-file behavior can inform a review when symbol resolution succeeds.
- Unresolved symbols are reported as missing context, not guessed about.
- Unrelated files are never sent to Gemini.

## 3. Add review modes and limits

- Add Fast, Balanced, and Deep review modes.
- Keep Fast mode limited to the selection and local context.
- Allow Balanced mode to resolve directly related workspace symbols.
- Require explicit user opt-in for Deep mode and larger token budgets.
- Make context and token limits configurable through VS Code settings.

Acceptance criteria:

- Users can trade review depth for speed and cost.
- Every request remains within its configured token budget.
- The output log reports mode, context sources, and actual token usage.

## 4. Improve review feedback

- Add a dismiss action for intentional behavior, separate from deleting a comment.
- Record dismissed issue fingerprints locally to avoid repeating known false positives.
- Add a command to review the same selection again with a stricter confidence threshold.

Acceptance criteria:

- Users can mark a suggestion as intentional.
- Repeated reviews do not continually reproduce dismissed findings.
- No source code or API keys are stored in feedback data.

## 5. Keep reviews responsive

- Cache parsed document context during a review session.
- Avoid scanning the entire document repeatedly for imports and definitions.
- Run Git and symbol lookups concurrently where possible.
- Add timing logs for context building, Git lookup, symbol lookup, and the LLM request.

Acceptance criteria:

- Review latency is visible in the output log.
- Context collection does not block the editor unnecessarily.
- Existing compile, lint, and extension tests continue to pass.

## 6. Add focused tests

- Test selection line numbering, including selections ending at column zero.
- Test context truncation and token-budget enforcement.
- Test Git diff filtering for overlapping and non-overlapping hunks.
- Test malformed, low-confidence, and out-of-range model responses.
- Test that comments remain attached to the original code editor when the output log has focus.
